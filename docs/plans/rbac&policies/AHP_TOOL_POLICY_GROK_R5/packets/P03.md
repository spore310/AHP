## Implementation steps

1. Build a bounded per-host in-memory registry/reference resolver for resource instances and trusted scoped bindings. Use domain/subject/agent identity, not a harness/model/display name. No singleton/global state.

2. Evaluate one complete current grant path plus every mandatory application/session/resource/provider constraint. Alternative grants need not all match; do not combine partial fields from unrelated grants into broader authority. Explicit deny/error/expiry wins.

3. Support direct-grant mode without artificial roles and role-restricted mode with application strings. Roles are resolved for the actual actor and scope. A provider and application can use different role labels; evaluate their meanings rather than intersecting strings.

4. Compile recipient assignments from canonical registered tools, type/resource admission, actual scoped grants and approved implementation bindings. Discovery, invoke, advertise, execute, propose, approve and publish remain independent operations.

5. Implement purpose-specific reveal conditions. reveal=true never adds an unknown/unassigned descriptor. The SDK materializes safe descriptors from canonical contracts; it never serializes arbitrary policy-returned metadata as trusted inventory.

6. Capture a revision/expiry stamp for decisions and expose a synchronous local freshness check used by later callers. Unknown resource or missing required evaluator denies; trusted inapplicability must be explicit.

## Required test coverage

| --- | --- | --- |
| A01 | No authority is the default | Empty policy/role/grant arrays assign no tools; explicit direct grant can work without namespace or invented role. |
| A02 | Valid scope-specific grant plus all constraints | Application allow/provider deny, missing evaluator and expired grant deny; same actor differs across scopes. |

| A05 | Caller and executor purposes are separate | Invoke-only recipient cannot advertise/publish; executor receives only its explicit execution assignment. |
| A06 | Reusable harness does not share authority | Two contexts using one harness/model name receive different exact assignments; no cross-user cache hit. |
