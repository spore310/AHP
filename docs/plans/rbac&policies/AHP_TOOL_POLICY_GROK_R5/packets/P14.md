## Implementation steps

1. Complete the trusted resource-kind registration port for current instance, exact application-defined resource type, owner/provider authorities, relationship revisions, supported operations and target resolution. Resolve type-level admission/mandatory policies through trusted registrations, never caller labels. Unknown/unregistered types fail unsupported/deny.

2. Use fake chat, terminal and workspace adapters to prove independent read/write/input permissions and trusted relationships, including a workspace or terminal associated with two sessions.

3. Carry both origin route and target resources through authorization. A caller cannot omit its chat-scoped origin or forge a relation to use a permissive session. Provider restrictions remain applicable to actual resources.

4. Implement optional application-owned result projection after validated execution. It requests a registered resource action through the owning service, with current policy and instance checks; it does not receive unrestricted mutable SessionState.

5. Ensure duplicate result cannot commit twice; revoked authority prevents sensitive result delivery/projection while cleanup still occurs. Distinguish execution success from projection/delivery failure and never automatically execute again.

6. Do not invent native chat/terminal reducer actions, spawn processes, mount filesystems or change work owner guards. Real runtime implementations remain separately supplied by a consumer.
