# P06 read-only integration preflight

**Status: PREFLIGHT ONLY — no P06 implementation authorization.** P05 is actively being written by Sol and remains the moving dependency boundary. This report relies on the accepted P03 handoff, P06 packet, immutable P01 contracts/constants, stable agent-directory and work-owner code, and the frozen P05 plan/amendment/authorization. I did not inspect active P05 source, P03 evaluator implementation, or `src/work/types.ts`; I made no source/test changes and ran no runtime, test, or DB commands.

## Recommendation

P06 should be a small **trusted in-process assign/revoke service over the existing canonical P03 registry**, not a parallel grant store or an IAM framework. It must resolve one exact issuer, target actor, resource instance and registered assignment rule; derive authority and lineage from canonical state; prepare asynchronously; then synchronously compare the captured revision basis and commit or deny. Revocation is a separate policy decision from assignment and invoke. Neither session ownership nor invoke permission implies either operation.

The main unresolved dependency is concrete: accepted P03 owns the authoritative resource/owner/binding/admission maps, but its accepted handoff does not expose a canonical BindingResolver reader, a public grant revision/lineage query, or the later P05 bootstrap IDs. Frozen P05 section 9 explicitly says a later canonical reader is a separate integration decision and must not become a second grant cache. Resolve that seam **after P05 acceptance and before P06 implementation** with a narrowly reviewed API amendment; do not build a shadow cache to bridge it.

## Minimum service and authority rules

The public service should be an in-process composition/API, not a JSON-RPC method in this packet. Conceptually:

```ts
assign(trustedIssuerContext, resolvedTargetActor, exactScope, requestedSubset, requestedExpiry)
  -> Promise<opaqueGrantReceipt>
revoke(trustedIssuerContext, exactGrantRef)
  -> Promise<void>
```

These are operation sketches, not approved public signatures. The actual context must come from the trusted adapter; target actor must be resolved by a trusted application port. Do not accept a wire-shaped `PolicyActorRef`, owner subject, role, parent authority or depth as proof. The request may express a bounded requested subset, but the service derives issuer, root/parent authority and depth from the captured registered rule and canonical store. Assignment/revocation are not additions to `TOOL_OPERATIONS`; no new `invoke` variant may stand in for them.

Each immutable, captured `RegisteredAssignmentRule` must separately specify:

- allowed issuer actor kinds and exact policy/role basis for `assign` and `revoke`;
- target actor kinds, exact allowed policy/role subset, and whether the scope must be identical or may be a verified descendant;
- finite maximum grant lifetime, maximum delegation depth, and whether a resulting grant may redelegate;
- which authority basis (registered host rule or exact live parent grant) may issue/revoke it.

No binding owner/admin property or `invoke` decision fills in an absent rule. A direct-policy grant still needs an explicit registered direct-assignment rule. A valid positive assignment only contributes one positive path; it cannot remove or replace an admitted ceiling or any mandatory restriction. Scope checks use a trusted relationship resolver over full canonical resources and a captured relationship revision, never URI prefix or caller labels. If no relation is registered, only exact full-scope equality is eligible.

P01 `GrantIssuer` is a useful service boundary, but the request needs an explicit contract decision before implementation: trusted issuer context should be a separate service argument (or trusted resolver output); `GrantAuthority`, depth, and parent basis must be derived, not caller-selected. Revoke must carry full expected `ResourceRef` plus binding ID and revision, not only URI/instance text. Any public `src/authorization/types.ts` change is a P01 contract amendment with dependent impact, not a silent P06 type edit.

## Canonical store, lineage and revision seam (required before implementation)

1. **One authority source.** Keep P03's existing binding map authoritative. Implement P04 `BindingResolver.read` and P06 issuer reads as adapters over that exact map/instance. Do not cache a second set of grant decisions/bindings in the issuer. Protected composition must prove exact store identity (or receive one combined canonical port); structurally similar but distinct stores are not coherent.
2. **Read basis.** Add a narrow immutable read surface on the same canonical registry: lookup an exact binding by opaque ID plus expected full scope; query bindings for an exact actor/resource; and obtain the monotonic local grant/relationship revision used by those results. Return a captured revision with the immutable bindings. This also gives P04's BindingResolver a reader without an unscoped read. Do not expose private bootstrap receipts as a new P04 wire view.
3. **Atomic local commit.** A prepared assignment captures actor/auth/connection-generation, full scope/instance, policy revisions, exact assignment-rule revision, relationship revision, grant revision, parent lineage/revisions and expiry. After awaits, one synchronous registry operation must compare all of those against current canonical facts and install the binding; no await/callback between final comparison and commit. Existing general trusted installation alone is not evidence of this CAS boundary. If the canonical P03 surface cannot provide it, P06 needs a reviewed, bounded registry amendment before implementation.
4. **Lineage.** Each child points to an exact parent grant incarnation and expected parent revision, not only `parentGrantId`; recursively resolve at most the captured depth limit. Verify exact issuer, actor/domain, full scope relationship, permitted roles/policies, redelegation right, and `child.expiresAt <= min(parent expiry, registered rule expiry)`. Reject cycles, missing/revoked/expired parents, overbroad target or any unknown revision. Keep `GrantAuthority.kind: host-policy` as the explicit root; the service, not the requester, selects it.
5. **No resurrection.** A revocation removes/invalidates every descendant and pending stamp dependent on the exact parent lineage. IDs are server-minted, never accepted from a request; revisions are positive and never rolled back within the host. Reissue gets a new ID or a strictly new incarnation/revision. Even if an ID is reused or advanced, old children must remain bound to the old parent revision/incarnation and must not become live again. The monotonic local grant revision changes on revocation, so an in-flight old stamp cannot become current after reissue. P05's random UUID/revision-1 bootstrap IDs are roots, not a justification to omit expected parent revisions. Restart invalidates these in-memory grants and continuations by default; no restoration is authorized.
6. **Cascade and event seam.** Exact parent revoke/expiry/teardown must synchronously invalidate descendants and tuples in the canonical map before reporting success. To avoid observers seeing a partial cascade, prefer one canonical batch mutation (exact expected bindings, one revision advance, one event); do not sequentially call a callback-producing remover and claim atomicity. The same local mutation seam must notify decision/assignment/continuation consumers of grant, policy, relationship and lifecycle revision changes. The authoritative revision changes synchronously; notifications are invalidation hints, not authority. Subscribers re-read canonical state and failures fail closed/quarantine rather than restore stale grants.
7. **Expiry/cleanup.** Check every ancestor expiry on access and at final admission, even if no timer ran. Bounded cleanup is supplementary and must cap work per pass; no unbounded descendant scan, per-grant timer, indefinite tombstone or durable restoration. Cap active grants, children per parent, grants per actor/domain, concurrent prepares/revokes and cleanup batch explicitly. Current constants provide depth/item/challenge values, not cardinality. A reasonable *proposal for the P06 plan gate*, not an existing limit, is active grants 1,024/host (absolute 4,096), 128/actor (absolute 1,024), 128 children/parent (absolute 1,024), and 64 pending mutations/host (absolute 1,024); check all counts before reservation/effects. Set a separately named finite grant-lifetime default and absolute cap; do not silently reuse challenge TTL or P05's separately purposed bootstrap lifetime. Lead must ratify all new count/lifetime values before implementation.

P01's asynchronous `FreshnessPort` remains an external freshness contract; it cannot be the sole final local gate. A local revision/currentness check and admission must be synchronous. A single canonical invalidation event should invalidate positive and negative decisions, assignment projections, and pending continuation stamps. No cross-system instantaneous-revocation claim: external resolvers supply their own expiry/invalidation bound.

## Session lifecycle and work boundary

P05's frozen plan expects future P06/P09 to deny failed/unavailable sessions; it also preserves a failed startup record and its canonical owner after withdrawing exact bootstrap. Therefore `owner(ref)` and `getResource(uri)` alone are insufficient readiness proofs. After P05 is accepted, confirm whether its SDK-owned factory capability exposes a read-only **exact-instance lifecycle/currentness** fact. If not, propose an explicit P05/P06 amendment for a narrow accessor that verifies `ResourceRef` identity and reports ready/failed/starting/disposing/unavailable plus a revision/currentness fence; it must project the factory's existing record, not maintain another state cache. Assignment and continuation checks deny any non-ready/failed/settling/stale instance. Startup failure invalidates any bootstrap-derived descendants and pending stamps before failure publication; teardown removes exact-instance descendants before the instance can be reused. A later same-URI resource is a different instance and cannot inherit grants or continuations.

Keep `src/work/helpers/helpers.ts`, repository/SQL contracts, lease fencing, owner projection equality and acting-principal inputs unchanged. No role, tool grant, parent grant, owner status, or same-harness identity authorizes another subject's durable work. A control should prove a non-owner with a valid tool assignment is still denied owner-only work using their own principal.

## Information boundary

Trusted in-process composition may need exact actor refs (including agent ID), canonical `ResourceRef`/instance, issuer and parent lineage, rule/policy revisions, relationship revision, expiry, local grant revision, and lifecycle/freshness result. Keep those as immutable internal contracts between trusted host adapters and the canonical registry. The network/wire must never supply or receive trusted actor classification, issuer authority, parent lineage, internal binding IDs/revisions, rule internals, grant maps, resource-owner facts, or freshness tokens. P06 adds no initialize/create fields, methods, descriptors, snapshot metadata, or assignment inventory. Later private projections require their own authorized protocol work under D3/P10/P12; an opaque result from an in-process service is not by itself permission to expose it.

## G01–G06 acceptance controls to carry into a later P06 plan

| ID | Positive control | Distinguishing negative / race control |
| --- | --- | --- |
| **G01 — use is not delegation** | A registered rule grants a narrowly bounded assignment to an explicitly authorized issuer; ordinary policy evaluation uses the resulting exact grant. | Owner, session creator, role holder, or actor with `invoke` but no `assign` rule cannot grant; no callback/registry mutation on denial. A separately authorized revoke right is also required; ownership alone cannot revoke. |
| **G02 — bounds and acyclic lineage** | Parent explicitly permits one in-scope child actor/policy with shorter expiry and allowed depth. Mandatory rules still participate in a successful operation. | Reject actor-kind/policy/role/scope overreach, unregistered descendant relation, mandatory-rule omission, excessive duration/depth/fanout, expiry after parent, missing/stale parent revision, cycle, caller-selected authority/depth, and ID reuse/advance attempting to revive a child. No partial install/capacity leak. |
| **G03 — ancestor revoke/expiry** | Exact root/parent chain grants a child and a positive decision before invalidation. | Revoke ancestor; descendant grant and assignments immediately deny, pending continuation becomes unusable, owner/resource/admission facts remain correct. Advance injected time past any ancestor expiry and deny on access before maintenance timer; bounded cleanup later removes stale entries. |
| **G04 — async freshness** | A stable captured revision completes evaluation and commits/admitted action. | Park policy/relationship/actor evaluation, revoke or change revision, then release: final sync gate denies before dispatch/send/commit. A timed-out, thrown or unavailable resolver also denies; no retry against a wider/fallback policy. |
| **G05 — no cache crossing** | Two actors/instances with independently registered valid grants each use only their own exact grant. | Same harness/model, role string, URI, actor ID text in another domain, connection/generation, or reused URI with new instance cannot reuse decision/assignment/continuation. Assert full actor/domain/scope/instance/executor and revision keys. |
| **G06 — owner-only work unchanged** | Existing owner submit/agent lease controls remain green under unchanged service behavior. | A non-owner with a valid session/tool grant still cannot submit/claim/complete as owner; actual subject remains the caller. Retain existing work tests and repository/equality checks; do not route an owner subject or alter lease/presence semantics. |

Also make lifecycle a cross-cutting negative: assignment and resume against starting, failed, unavailable, disposing or stale instances deny. Include a ready positive, a P05-style inspectable startup-failure record whose bootstrap is withdrawn before failure notification, teardown/late async completion, and a same-URI successor with a fresh instance. These are required controls, not claimed results.
