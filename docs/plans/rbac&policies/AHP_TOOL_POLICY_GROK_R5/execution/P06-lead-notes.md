# P06 planning constraints — refresh after P05 acceptance

**Planning notes only, not an approved API or implementation assignment.** Read Luna's `P06-preflight.md`; actual P05 APIs/hashes must be refreshed after acceptance. Do not inspect or modify active P05 implementation to turn assumptions into facts.

- Verified stable `src/toolPolicy/constants.ts`: ToolOperation is discover/propose/approve/advertise/publish/invoke/execute; **assign/revoke are not existing tool operations**. Do not invoke P03.evaluate with invented operation strings or infer assignment from invoke/owner. Prefer an authorization-owned registered grant-control capability with an explicit issuer basis and bounds, keeping future child tool use subject to unchanged admission and mandatory rules. Exact signatures/basis semantics need the P06 plan gate.
- Canonical bindings, ancestor revision metadata, mutation revisions and invalidation must stay with one registry. The service may retain bounded pending preparation receipts, not a second authoritative live-grant/role cache. A trusted scoped reader/revision adapter is needed so P04 initial authority can read actual P05-created bootstrap bindings; no unscoped wire query or leaked grant inventory.
- Parent ID alone is not enough. Bind children to the actual parent revision/incarnation and resource/relationship basis; removal/reissue cannot revive descendants. Check ancestor expiry on access without waiting for cleanup. P05's owner-retaining removeBinding on backend failure must invalidate dependent authority as well as direct tuples once delegation exists.
- Keep prepare asynchronous and final commit/rollback local and synchronous. All external policy/actor/relationship/readiness/currentness callbacks run before the last internal canonical comparison and commit. Recheck after callbacks so reentrancy cannot invalidate an already-performed final check. Pending receipts are per-service issued objects, single-use, bounded, cancellable and released on late completion.
- P06 is trusted in-process service work, not new wire methods. Preserve P01 ports unless an exact reviewed amendment is necessary; an adapter may bind a richer trusted issuer context rather than accepting request.issuer/authority/depth as proof. Roles/policies/target fields express intent constrained by the registered rule and canonical basis, not authority.
- After P05, verify a minimal exact-instance lifecycle/readiness projection exists or propose one explicitly; owner existence is not ready/usable state. Do not manufacture another lifecycle cache. Failed/starting/settling/stale resources cannot receive participant delegation or later execution.
- Invalidation changes canonical revision synchronously; subscriber notifications are hints, not a permission source. Design bounded cascade/work limits and handle observer failures/reentrancy without partially publishing authority or recalling admitted remote effects.
- Keep work implementation/owner equality/leases unchanged. Actual caller stays the caller even when granted tools in another owner's session.

These constraints are inputs to a later exact plan. Do not freeze new cardinality/lifetime values or broad P03/P05/P01 API changes from this note; assess against the accepted implementation and approve the smallest coherent seam first.
