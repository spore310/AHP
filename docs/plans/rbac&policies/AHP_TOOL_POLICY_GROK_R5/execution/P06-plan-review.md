# P06 independent plan review

**Verdict: REVISE — do not authorize implementation yet.** This was a read-only review of Sol's proposal, not an implementation or a P06 acceptance. I read the complete `P06-plan.md`, `packets/P06.md`, `CONTRACT_CARD.md`, `contracts/AUTHORITY.md`, `contracts/DELIVERY_WIRE.md`, `P06-preflight.md`, `P06-lead-notes.md`, and the accepted P05 handoff/integrity evidence; I checked the relevant current P01/P03/P04/P05/agent/work interfaces. No source/tests/runtime/DB commands or children were used. P05 is accepted on the recorded 106-file candidate hash `97f8c95f904c9357ee4c8b89fc5d53ee261fc603d2c4bc8e418d78aec7252121`; its reported 72-file/684-test/163-source validation is predecessor evidence, not a P06 check. The review findings below are plan/source-inferred; no runtime behavior was reproduced.

## What the proposal gets right

The central architecture is sound: extend P03's canonical binding/resource maps rather than create a grant cache; model root and delegated issue/revoke authority separately from invoke/ownership; preserve P01 port signatures; capture async decisions and use a synchronous final compare-and-commit; fence children by parent incarnation/revision and resource relationship; retain P05 failed-record ownership while cascading bootstrap withdrawal; keep work equality/leases and the wire unchanged. Proposed expiry-on-access plus bounded complete closure cleanup is consistent with expiry being authority loss, not a timer promise, provided the full scan/closure is bounded by captured existing caps and uses one sampled time with no callbacks inside mutation. The plan distinguishes the new pending/list/lifetime budgets from P05 bootstrap, P01 challenge, and existing total `maxBindings` budgets; all proposed values remain explicitly unratified. Its outbox is correctly described as a hint, not authority, and it avoids invented `ToolOperation`s.

## Required revisions

### R1 — the required readiness capability is not forwarded by the actual composed host (P2, scope/consumer mismatch)

The proposal makes `SessionFactoryAuthorization.isReady(expected)` required (§2.3), and the proposed execution list changes its type/implementation, but omits the actual wrapper in `src/websocket/helpers/host/helpers.ts`. That file constructs `hostedAuthorization` as a `SessionFactoryAuthorization` object at lines 181-198 and currently forwards only `createSession`, `getResource`, `isSettling`, and `disposeSession`; `AHPServerHandle.sessions` exposes that wrapper (`src/websocket/helpers/host/types.ts:44-48`). A required member added at `src/sessions/helpers/creation/types.ts` therefore makes this object incomplete at typecheck and, more importantly, leaves the capability unavailable to the supported composed host. P06's planned service has no alternate specified way to obtain this factory-owned readiness fact from that host.

**Smallest resolution:** add `src/websocket/helpers/host/helpers.ts` to the exact future scope and forward the captured original `isReady` through the host wrapper (or revise the design so the service uses a concrete capability already reachable through the actual composed host; do not make a required method optional merely to compile). Add a real composed-host readiness test to the planned `freshness.test.ts`: creating/failed/settling/stopped and stale same-URI instances deny; a ready exact instance passes. This is one additional required source path, so the current “exact 17 paths” is not yet feasible as written.

### R2 — P04's binding read is revision-checked once, but its returned currentness is not tied to the canonical revision (P1 security-integration contract; P2 missing distinguishing test)

The proposed `BindingResolver` adapter (§2.1) can reject a stale `query.grantRevision` while the individual read runs, and the proposed canonical `readBindings` can discover P05 bootstrap bindings. That alone does not fence the *prepared P04 connection* after the read. In the actual P04 path, `createConnectionSetupAdapter` reads bindings once at `src/websocket/helpers/security/helpers.ts:168`, then returns `isCurrent` at `:194` as `current() && now() < validUntil`; `current()` at `:126-138` checks the `PreparedInitialScopes.isCurrent` callback, abort, and time, not P03's grant revision. The transport and native create gate later rely on that closure (`src/websocket/helpers/connection.ts:303-313`; `src/websocket/helpers/ahp/helpers.ts:20-27,50-60`). The plan says P04 must “retain/recheck its canonical fence” but does not specify how the actual `InitialAuthoritySource`/`PreparedInitialScopes.isCurrent` supplied in this composition obtains and rechecks that fence. A lossy invalidation hint cannot substitute for that final currentness check.

**Smallest resolution:** specify that the P04 composition seeds each `InitialBindingScope.grantRevision` from the canonical scoped reader, and that its synchronous `PreparedInitialScopes.isCurrent` re-reads/compares the exact canonical revision (or uses an equally strong SDK-issued currentness check) on every final P04 guard; it must not rely only on `FreshnessPort` domain revision or event delivery. Add a `freshness.test.ts` integration case using the real `createConnectionSetupAdapter` and an actual P05-created bootstrap: read the bootstrap at the captured revision, mutate/revoke the canonical basis after the binding read, then prove the prepared setup/currentness and protected native admission fail closed. If this is instead intentionally outside P06, narrow the P06 claim and record the missing P04 integration as a lead-owned prerequisite, not as already satisfied by `BindingResolver.read`.

### R3 — the new incarnation fences are not carried through existing conditional cleanup APIs (P2, ABA semantics incomplete)

The internal `CanonicalBindingToken` (§2.1) adds `incarnation`, and §4 correctly says removal/reinstall of even the same ID/scope/revision must mint a new identity. But current P03 conditional removal does not accept that identity: `ReferenceAuthorizer.removeBinding` is only `{bindingId, scope, revision}` (`src/authorization/helpers/evaluate/types.ts:166`; implementation `helpers.ts:645-665`). P05's delayed startup-failure withdrawal still stores only those three fields (`src/sessions/helpers/creation/helpers.ts:198,210-212,350-352`); `installBinding` returns `void` (`types.ts:177`, implementation `helpers.ts:702-719`). Thus a captured P05 cleanup for `(B,S,1)` can run after `(B,S,1)` is removed and reinstalled, and match/delete the successor despite the successor having a different private incarnation. The same gap exists for exact resource teardown: `teardown(resource)` carries no expected installation token (`types.ts:183`; implementation `helpers.ts:800-815`), although §4 proposes a private resource installation incarnation and the plan specifically requires same-full-ref reinstall/ABA safety.

**Concrete source-level interleaving:** attach a P05 bootstrap binding `(B,S,revision 1)`; park the asynchronous backend start; trusted canonical cleanup removes it and a legitimate replacement is installed with the same ID/scope/revision; the old startup's `beforeFailure` later runs the P05 receipt and calls `removeBinding({bindingId:B,scope:S,revision:1})`. The accepted P05 callback is allowed to run after an await, and the current port cannot distinguish that replacement. Analogously, a delayed teardown holding only full-ref `R` cannot distinguish a later reinstallation of the same full-ref text.

**Smallest resolution:** define token-bearing install receipts and exact expected-token removal/teardown for SDK-owned cleanup; capture the token at P05 install time and use it for bootstrap withdrawal and resource teardown. Keep any legacy trusted administrative operation explicitly distinct if compatibility requires the current signature. Add same-ID/scope/revision binding ABA and same-full-ref resource teardown ABA tests in the new P06 tests. The existing P05 helper/type files are already in the proposed set, but their use must be an explicit narrow P05 integration amendment; do not claim the 17-path implementation is safe until lead approves it and the exact tests/README impacts are included.

## Bounded decision review / remaining plan gates

- **Lineage and descendants:** the same-map envelope, explicit `grantParent`, one parent incarnation, full actor/domain checks, finite depth, and closure staging avoid a shadow child index. Keep resource-parent and grant-delegation depths separate. Ensure rebinding a relationship invalidates all old captured paths even if it is later restored; closures must be complete before one mutation publishes. The R3 cleanup-token gap is the remaining ABA hole.
- **Expiry pruning on access:** the design is acceptable as a target if it scans only the bounded canonical maps, takes one finite sampled time, stages a union closure, and commits once without callbacks. `maxCleanupRoots` should bound maintenance selection only; it must not truncate a selected root's dependent closure. G03/G03 no-sweep access tests should assert both a genuine pre-expiry allow and denial after advancing injected time without running maintenance. Avoid interpreting a lossy event as expiry enforcement.
- **Event coalescing/loss:** the one-notice outbox is not an authority source, so dropping/coalescing hints is safe only because every consumer must compare canonical revisions at use. The plan explicitly leaves reentrant pending hints for a later explicit drain; identify the SDK owner/call site that invokes `drainInvalidations`, or state plainly that the hint is best-effort and downstream views cannot use it as their sole freshness mechanism. Never make P04 currentness or final grant admission depend on notification delivery.
- **Draining callbacks/cleanup:** a shared service pool held until all target/approval invocations, returned async release, and receipt cleanup actually settle is coherent; disposal may reject callers promptly but cannot reset occupancy. Keep the pool per canonical registry, count across issuer contexts, and prove late cleanup cannot free another slot. Clarify that a never-settling `rollback`/cleanup leaves the receipt slot occupied rather than claiming it has been released.
- **Limits:** no obvious contradiction with accepted P05/P01 defaults: `maxBindings` remains the one total registry cap; `maxAdmissionInstalls` remains a separate accepted P05 per-call cap; challenge, bootstrap, grant lifetime, resource depth, rule/input, mutation, actor, child, cleanup and observer bounds have distinct purposes. They are proposals only and must be ratified before implementation. Preserve `ReferenceAuthorizer` input capture and exact higher-budget compiler selector compatibility from P05.
- **P01/operation/work boundaries:** the P01 ports in `src/authorization/types.ts` can remain unchanged if `GrantIssueRequest.issuer/authority/delegationDepth` stay assertions and the service supplies trusted bound context separately. No new `ToolOperation`, owner/invoke-derived assign/revoke, work owner substitution, SQL, or wire payload is warranted. P04's `BindingResolver` can read actual P05 bootstrap IDs via a scoped canonical reader, subject to R2's currentness composition.
- **Scope/fixtures:** the proposed 17 paths are otherwise reasonably bounded; `createAHPServer`'s wrapper omission is the concrete missing production consumer above. I found no basis to migrate the seven internal or eighth public transport suite wholesale. The two new suites can host the P04/P05 readiness and ABA controls. Do not add the preflight's intentionally uninspected work types or alter old assertions without a demonstrated conflict and exact scope approval.
