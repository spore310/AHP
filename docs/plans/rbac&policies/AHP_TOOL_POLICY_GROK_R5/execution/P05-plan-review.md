# P05 independent plan review

**Verdict: REVISE before the P05 plan/write-set gate. P05 implementation is not authorized.** This review used the P05 packet, AUTHORITY/INTEGRATION, stable session/work/P03 implementation, `P05-plan.md`, `P05-preflight.md`, `P05-lead-decisions.md`, and the accepted direction in `P04-sequence-resolution.md`. I did not inspect the changing P04 implementation, run tests/runtime/DB commands, edit source/tests, or use children. P04 remains unaccepted; its correction and a later independent recheck remain prerequisites.

## Findings and required amendments

### P05-1 (P1): The proposed policy/compiler pair does not prove one coherent admission authority

`P05-plan.md` configures `creationSecurity` with both a `ReferenceAuthorizer` registry and a separate `ToolPolicyFactory`. It compares the session type's rules with `creationSecurity.policies.forSessionType(...)`, then calls `registry.installAdmission(...)`. But `createReferenceAuthorizer` captures its own `policyRegistry` from its constructor, and `installAdmission` obtains the actual admission rules from that private compiler (`src/authorization/helpers/evaluate/helpers.ts`, `createReferenceAuthorizer` / `installAdmission`). The current `ReferenceAuthorizer` interface has no compiler provenance or rule-inspection operation. The passed `policies` object can therefore agree with the type declaration while the registry's hidden compiler has different, wider rules; `installAdmission` installs the latter. The plan's assertion that both inputs “reuse the same compiler” is not established by its stated comparison.

This is a trusted-composition mismatch rather than a wire attack, but it can make the protected admission differ from the exact registered type ceiling. A prose-only same-instance obligation is not enough for the plan's claimed fail-closed construction check.

**Amendment:** make coherence enforceable at the registry boundary. For example, have one opaque construction/composition return both capabilities from the same compiler, or add a P03-local validation/installation seam that compares the supplied exact rules against the authorizer's captured compiler before installing admission. Do not add a P06 issuer or silently trust two uncorrelated authorities. Add a mismatch control: a registry built with broader rules and a separately supplied narrower compiler/type must fail during construction, before any resource, record, binding, or public effect. Because the current P05 conditional P03 amendment only covers `removeBinding`, this coherence seam needs its own exact P03 write-set/lead approval if it changes P03. A documented adapter obligation is acceptable only if the plan removes the misleading “validated” claim and records a lead-approved, auditable single-construction contract that makes mismatched pairs impossible to supply through the protected host surface.

### P05-2 (P1): Native creation must depend on successful cursor-authorized initialize, not merely a live P04 context

The accepted P04 sequence direction requires public native initialize to have a current setup snapshot with captured `allowGlobalSequence === true`; that permission authorizes only disclosure of the genuine shared cursor. The P05 public create section currently requires a P04 snapshot/currentness/fence but does not expressly require the native peer to have completed that successful initialize before it reaches the factory capability. A setup snapshot, even one with cursor permission, is not creation authority; conversely, a setup without cursor permission must not obtain native initialization or create by sending `createSession` first.

**Amendment:** state that the *network AHP create route* is reachable only after successful `ready` initialization on that same connection and requires the captured P04 cursor permission to remain current. A rejected/unattempted initialize, a false/missing permission, or JSON-supplied permission fields must not call the creation callback or touch reservation/record/resource state. Keep the distinction explicit: `allowGlobalSequence` is protocol-metadata permission only; creation still requires the separate exact type/provider creation callback and bootstrap approval. Do not make the cursor permission a session grant or a prerequisite for unrelated trusted in-process creation APIs. Add paired tests: live setup + false cursor permission (and pre-initialize request) has zero creation effects; explicit cursor permission plus a separate denied creation decision still denies; successful initialize with cursor permission plus separate creation approval may create and returns only `null`.

### P05-3 (P2): Resolve the session-URI/resource-ID bound and avoid widening the established input byte ceiling

The current `sessionUriSchema` only requires the `ahp-session:/` prefix and a nonempty suffix. Work independently caps URI length at 2,048 (`src/work/helpers/helpers.ts`), while the default P03 `resourceRefSchema` caps resource IDs at `POLICY_LIMIT_DEFAULTS.maxResourceIdLength` (512; `src/authorization/constants.ts` and `src/authorization/helpers/validation/helpers.ts`). P05's candidate `ResourceRef.id` is the URI, but the plan does not define which accepted bound protected creation enforces. A URI accepted by the existing session/work surface can therefore be unusable as a P03 binding scope unless creation rejects it before reservation/approval.

The proposed `maxCreationInputBytes` default of 1 MiB matches `WEBSOCKET_MAX_PAYLOAD_BYTES`, but the 16 MiB absolute option lets a direct factory capability accept materially larger creation input than the public transport. The plan should say whether that is an intentional trusted-only distinction; otherwise the same bounded creation-input ceiling should apply to both entry points. The already-existing async hook deadline and 60-second decision horizon are appropriately reused. No current policy limit has the same semantic purpose as creator-bootstrap binding lifetime; its P05-local cap may remain if explicitly justified rather than being conflated with challenge TTL.

**Amendment:** specify and test the effective protected session URI limit against the P03 resource-ref validator before callback/reservation, with at-limit and one-over cases. Align the public and contextual factory creation input budget, or document a narrowly trusted-only reason and prove public input cannot exceed the transport ceiling. Keep distinct per-attempt bootstrap-binding count and grant-lifetime budgets only where they bound different state from registry capacity/decision TTL; do not introduce a second name for an existing identical-purpose limit.

## Plan strengths confirmed

- The creation callback is separate from invoke/issuance, receives exact registered type/provider, candidate instance, actual caller and immutable normalized input, and can only approve an SDK-materialized template. The client cannot choose owner, actor, roles, binding identity, authority or scope.
- Exact type registration/capture is detailed: serializable definitions omit executable policy code, policy/parser/provider callbacks are captured privately, header selection resolves a uniquely enabled registered revision, and policy admission/mandatory sets remain separate. The template's admitted policies stay within the positive ceiling; mandatory bindings cannot be promoted into an alternative allow path.
- The URI reservation precedes asynchronous preparation; cancellation/stop rejects late attach and releases late preparations; the final currentness/reservation check is adjacent to no-await attach. Attach rollback is exact-instance and precedes publication/backend start.
- The selected S05 failure behavior follows AUTHORITY A5 and the lead decision: retain inspectable failed record and immutable owner, withdraw only newly installed bootstrap bindings before failure publication. The conditional `removeBinding(expected bindingId/scope/revision)` proposal is a narrow fit: stale/mismatched requests no-op, ownership/resource/admission remain, associated assignments and issued currentness are invalidated. It correctly requires an explicit P03 amendment and its own exact positive/negative tests; it is not currently authorized.
- The owner projection is read-only and derives subject from the live record's full resource ref and canonical P03 owner within the configured work domain. A separate finite expected-instance settle marker retains lifecycle exclusion without retaining owner subject. WorkService equality/lease behavior remains unchanged; no participant is promoted or substituted as owner.
- S01–S05 coverage is concrete and generally distinguishing: separate subjects/owner, explicit creation and template approvals, injected partial-install rollback before publication, same-URI/late-callback races, and failed-backend owner retention with stale bootstrap invalidation. Preserve old lifecycle tests and their assertions. Add the coherence and native-cursor cases above, and ensure S02 distinguishes a type that *requires* its declared template (where `kind: none` denies) from a type with no template (where explicit `kind: none` may be valid).
