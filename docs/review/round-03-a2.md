- **Evidence (exact path, frame → SQL):**
  - Frame: `{"jsonrpc":"2.0","id":1,"method":"disposeSession","params":{"channel":"ahp-session:/x\u0000"}}` sent by the session owner (owner === principal passes the guard) — or any unauthenticated/baseline connection while no owner binding exists.
  - `src/websocket/helpers/ahp/types.ts:46-49` — `channelParamsSchema = z.object({ channel: z.string().min(1) })` (contrast `agentWork.ts:115-118` where every work-path URI carries `.max(2_048)` + `isJsonbSafeText`).
  - `src/websocket/helpers/ahp/helpers.ts:403-415` — parse, owner guard, then `work.assertSessionDisposable(parsed.channel)` (line 412); errors mapped at 413-415 via `mapWorkError` → `mapRepositoryError` (`agentWork.ts:180-190`), where `code: "database"` → `RpcError(JsonRpcErrorCodes.InternalError)`.
  - `src/work/helpers/helpers.ts:386-394` — `assertSessionDisposable` applies **no text predicate** (contrast the service's own sessionUri gates on `submit` at helpers.ts:75-80 and `claim` at 255-260, added by rounds 1–2).

  - Same service path without schema at all in the host facade: `src/websocket/helpers/host/helpers.ts:168-185` (`channelFromParams` accepts any string; the facade's `assertSessionDisposable` and unbind run before/independent of the AHP handler).
- **Why not accepting it as hypothetical:** it is client-controlled input on a live frame (owner-scoped session), one hop from SQL; the fix pattern already exists one file away (`agents` directory gate, `directory.ts:89-92`).
- **Proposed fix (non-contract):** apply the shared predicate at the dispose boundary — `WorkService.assertSessionDisposable` gate on `isJsonbSafeText(sessionUri)` (throw `WorkError("invalid")`) — or gate the AHP dispose channel with `isJsonbSafeText` + a length cap before line 412; either covers the facade path. No `types.ts` change.

### F2 — P3, `open` — unbounded recursion in the shared `isJsonbSafe` predicate overflows the stack for a client-deliverably-deep `input`/`result` and escapes as an unclassified `Internal error`

- **Claim:** the wire payload-bounding refine (and the service's `boundedJsonBytes`) recurse with no depth budget; a frame well under the 1 MiB cap can throw `RangeError` past `JSON.parse`, past Zod, past the handler's `try`, and the dispatch loop answers `Internal error` instead of a typed invalid.
- **Evidence:**
  - `src/persistence/helpers/text.ts:40-53` — recursive `isJsonbSafe` (3+ JS frames per nest level; no depth guard).
  - Wire trigger: `src/websocket/helpers/ahp/agentWork.ts:99-105` → `boundedObject`/`boundedResult` refine → `isBoundedInput`/`isBoundedResult` (77-97) → `isPayloadInvalid` (70-75) → `isJsonbSafe`; the parse call (`agentWork.ts:365`, `submitSchema.parse`) sits **outside** the handler try (begins line 367), and `completeSchema.parse` (line 425) likewise precedes its try (line 426).
  - Escape path: `src/websocket/helpers/connection.ts:173-180` catches handler failures → `sendMappedError` (127-139): not `ZodError`, not `RpcError` → `JSONRPC_INTERNAL_ERROR`, "Internal error". Contained per frame, no crash.
  - Frame depth available: `WEBSOCKET_MAX_PAYLOAD_BYTES = 1_048_576` (`src/websocket/constants.ts:13`); a `{"a":` ladder of 5 bytes per level supports ~191k depth.
  - Review-time probe (read-only scratch script in the approved temp dir; **no SQL executed, no repo files touched**): on plain Node 24, `JSON.parse` did **not** fail at any depth probed to 160,000, while the `isJsonbSafe`-shaped recursion RangeError'd at depth ≈ 3,000 (`Maximum call stack size exceeded`). So the overflow input is well within the frame cap and parseable.
  - Service-layer mirror: `src/work/helpers/helpers.ts:33-46` — `JSON.stringify` is inside a try (deep-throw → typed `invalid` ✓) but `isJsonbSafe(value)` at line 43 is not; `assertSubmission` is invoked before `submit`'s try (line 183), so a direct-service caller sees the raw RangeError. On the real wire path the refine throws first.
- **Severity rationale:** same fault class the panel consistently graded P3 (unclassified 500-class reply on client-controllable input; no process crash, no state corruption — the reply path is caught and sent).
- **Proposed fix (non-contract):** add an explicit depth budget to the `isJsonbSafe` recursion in `text.ts` (reject beyond e.g. 1,000 levels with the same boolean), or catch `RangeError` in `isPayloadInvalid`/`boundedJsonBytes` and map to the domain `invalid`. One sentence of either also makes the session-projection gate insult-proof.
